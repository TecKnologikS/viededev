Claude Ship : l'activer et s'en servir

bfe80d124 nov. 20267 min de lecture#ia #claude-code #github

Anthropic a sorti Claude Ship le 23/11/2026, en bêta. Claude relit tes pull requests, pousse les corrections, et peut les approuver si les règles de ton équipe le permettent.

D’où vient ce guide. Il suit la documentation officielle, lue en entier le 24/11/2026. Je n’ai pas pu activer les agents moi-même : mes dépôts sont sur Forgejo, et Claude Ship ne marche qu’avec GitHub. Les noms de menus sont ceux de la doc, en anglais. Le produit est en bêta, ils peuvent bouger.

Ce que c’est

Une commande et trois agents.

  • /ship, dans Claude Code : elle ouvre ta pull request, la relit et la répare, depuis ton terminal.
  • Code Review : relit chaque pull request et laisse des commentaires classés par gravité. Disponible pour tous.
  • PR Steward (bêta) : répare la CI en échec, les conflits de merge et les retours de review. Il n’approuve pas et ne merge pas.
  • Claude Approvals (bêta) : applique un fichier de règles écrit par l’équipe. Selon ces règles, Claude approuve ou demande un humain.

Pour qui

  • Les agents demandent une offre Claude Team ou Enterprise.
  • Les dépôts doivent être sur GitHub.
  • Exclus : les organisations en Zero Data Retention, en configuration HIPAA, ou avec leurs propres clés de chiffrement.

Pour /ship seule, la doc ne dit pas si une offre Pro ou Max suffit. Elle dit seulement que la commande tourne dans ta session et compte dans ton usage.

L’essayer seul : /ship

C’est le plus court chemin : rien à activer côté admin.

Il te faut :

  • Claude Code 2.1.330 ou plus récent ;
  • GitHub CLI 2.63 ou plus récent, connecté avec gh auth login ;
  • git 2.38 ou plus récent.

Depuis le clone local de ton dépôt, dans Claude Code :

/ship

Ce qui se passe, dans l’ordre :

  1. Pull request : Claude commit ton travail, pousse la branche et ouvre la pull request à ton nom. Si tu es sur la branche par défaut, il crée une nouvelle branche et bascule dessus.
  2. Review : il lance /code-review sur ton changement.
  3. Surveillance : il continue de regarder la pull request et pousse des corrections pour la CI en échec, les conflits et les commentaires.
  4. Merge : c’est toi qui merges.

Trois choses à savoir avant de la lancer :

  • Pas de confirmation. Avant le commit et avant le push, une ligne finit par « Esc to cancel ». Si tu ne fais rien, ça continue au bout de quelques secondes.
  • Pour arrêter : /ship stop dans la session qui la fait tourner.
  • Annulé après le commit ? git reset HEAD~1 défait le commit en gardant tes fichiers.

Quelques arguments utiles :

/ship low          # review plus légère (low, medium, high, xhigh, max ; high par défaut)
/ship 41           # travaille sur la pull request 41
/steward           # surveille une pull request déjà ouverte, sans la relire

Sur un dépôt qui n’est pas sur GitHub, /ship n’ouvre pas de pull request, mais relit quand même ton changement.

L’activer pour une équipe

Il faut le rôle Owner de l’organisation Claude. Tout se passe dans Organization settings > Claude Ship.

La doc conseille d’activer un agent à la fois, sur un seul dépôt, dans cet ordre : Code Review, puis PR Steward, puis Claude Approvals.

1. Code Review

  1. Active l’interrupteur sous Review, puis clique Turn on.
  2. Si une fenêtre Connect GitHub s’ouvre, clique Connect et autorise Claude.
  3. Si tes dépôts n’apparaissent pas, clique Install GitHub App : choisis l’organisation GitHub et les dépôts. Il faut être propriétaire de l’organisation GitHub.
  4. Sélectionne les dépôts et valide l’ajout.
  5. Dans « Choose what Claude does on these repositories », laisse Code review coché, décoche Steward pour l’instant, puis Turn on.
  6. Ouvre une pull request de test, pas en brouillon : une vérification nommée Claude Code Review apparaît en quelques minutes.

Deux réglages par dépôt, avec le bouton Edit de sa ligne :

Réglage Choix
Review level Quick (le plus rapide, le moins cher), Standard (par défaut), Deep (le plus poussé, le plus cher)
Review runs Once after PR creation, After every push (par défaut), Manual (@claude review)

En manuel, un commentaire @claude review sur la pull request lance la review. Les brouillons et les pull requests venues d’un fork ne sont jamais relus automatiquement.

2. PR Steward

Avant de l’activer, la doc demande une règle de branche qui exige une pull request avec au moins une approbation sur la branche par défaut.

  1. Sous l’interrupteur Steward, choisis pour qui il tourne (Runs for) : tout le monde, ou une liste de comptes GitHub.
  2. Clique l’interrupteur Steward, puis Turn on.
  3. Fixe une limite mensuelle : Organization settings > Usage, section Services, ligne PR Steward.
  4. Sur la ligne du dépôt, Edit : règle Steward sur Manual (@claude steward) et fixe un plafond par pull request avec Steward spend cap.
  5. Teste : commente @claude steward sur une pull request. Le label claude-pr-steward-watching et un commentaire « Claude PR Steward » apparaissent.

Pour l’arrêter sur une pull request, retire ce label.

3. Claude Approvals

Il s’active en ajoutant un fichier .claude/approvals.yml à la racine du dépôt, sur la branche par défaut. Voici le modèle de départ de la doc :

# .claude/approvals.yml
version: 1
mode: observe
rules:
  - purpose: "A change takes two people. When Claude's review passes, one is enough and Claude approves."
    paths: ["**"]
    verdict: { claude: comments, seats: 2 }
    override:
      - { if: "claude/code_review = pass", verdict: { claude: approves, seats: 1 } }
  - purpose: "A change to the review rules takes two people."
    paths: ["**/.claude/**"]
    nested: inherit
    verdict: { claude: comments, seats: 2 }

Ce que dit ce fichier : un changement demande deux personnes. Si la review de Claude passe, une seule suffit et Claude approuve. Un changement des règles elles-mêmes demande toujours deux personnes.

Commence en mode: observe. La vérification montre ce que les règles auraient décidé, sans que Claude approuve quoi que ce soit.

  1. Ajoute le fichier dans sa propre pull request.
  2. Merge quand Claude commente que le fichier est valide.
  3. Ouvre une autre pull request : une vérification Claude Approvals apparaît, avec un titre qui commence par « (observe mode) ».

Pour passer en vrai :

  1. Supprime la ligne mode: observe et merge. Sans cette ligne, les règles s’appliquent.
  2. Cinq minutes plus tard, commente @claude approvals rerun sur les pull requests encore ouvertes.
  3. Dans les règles de branche GitHub, rends la vérification Claude Approvals obligatoire.

Ce que ça coûte

  • Chaque agent est facturé aux tokens, sur les crédits d’usage de l’organisation, en plus de l’abonnement.
  • /ship et /steward comptent dans ton usage normal de Claude Code.
  • Claude Approvals n’a pas de coût de base, mais des règles qui s’appuient sur la review de Claude déclenchent une Code Review facturée, même en mode observe.
  • La doc ne donne pas de prix : tout dépend de la taille des pull requests et du niveau de review.

Les pièges

  • PR Steward n’a aucune limite de dépense tant que tu n’en mets pas. Et la dépense peut dépasser le plafond avant qu’il s’arrête.
  • Auto-merge. Avec l’auto-merge ou une file de merge GitHub, des règles qui n’exigent pas l’approbation d’une personne laissent un changement partir sans que personne n’agisse.
  • Ajouter un dépôt peut lancer Code Review dessus, et c’est facturé.
  • Couper les crédits d’usage n’arrête pas un agent : s’il est activé, il continue de tourner et de facturer.
  • Windows natif : /ship ne lance pas de surveillance.
  • Les sessions cloud n’ont ni /ship ni /steward.
  • La surveillance de /ship : ne la lance que là où tu fais confiance à tous ceux qui peuvent pousser sur ta branche ou merger sur la branche de base. La doc prévient qu’ils peuvent faire tourner des programmes sur ta machine, avec tes accès.
  • Pour tout arrêter, dans cet ordre : Approvals, puis PR Steward, puis Code Review.

Et l’avertissement d’Anthropic, à garder en tête : Claude Ship peut rater des bugs et des failles de sécurité.
